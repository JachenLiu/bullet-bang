# Bullet Bang architecture

## Authority boundary

Photon Fusion state authority owns every table and match. Clients send intent
(`join`, `draw`, `play`, `respond`, `discard`, `end turn`) and never send resulting
health, cards, roles, or distance values. The server validates intent with
`BangRules`, changes the match, and publishes a filtered `MatchView`.

## Privacy boundary

`MatchProjection.For(match, playerId)` contains that player's private hand and
role. `MatchProjection.For(match, null)` is the spectator projection and contains
only public information. Network code must not serialize `BangMatch` directly.

## Presentation boundary

The 3D card, cameras, animations, UI, sound, and table props visualize confirmed
match events. They never decide whether a move is legal. Lobby avatars use a
third-person camera; seated players use first-person; spectators follow a selected
public player camera without inheriting that player's private UI.

## Expansion boundary

Base deck composition lives in `BaseGameCatalog`. New expansions should provide:

1. A content catalog containing cards and characters.
2. Rule modifiers/effect handlers registered with the match rules layer.
3. Optional presentation handlers for new events.

Expansion code must not fork the turn manager or replace lobby/table networking.

## Scene workflow

`Assets/Scenes/MainLobby.unity` is the only runtime scene. A table changes a
player's interaction and camera mode; it does not load another scene. This keeps
roaming players, concurrent matches, and spectators inside one Fusion session.
Legacy gameplay/test scenes remain disabled in Build Settings for reference.

The active runtime path is `MainLobbyManager` → `GameTable` → `GameSession`.
`NetworkManager`, `NetworkRunnerHandler`, `LobbyManager`, and `LobbyUIManager`
are retained prototype components but must not be added to `MainLobby`; running
more than one networking entry point would create competing Fusion runners.

The lobby environment is generated by the Editor scene builder. Generated
geometry is grouped beneath a single root, so visual iteration can replace it
without disturbing the network manager, UI, or prefab references.
